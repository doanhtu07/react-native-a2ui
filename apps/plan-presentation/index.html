A2UI v0.9 on React Native

react-native-the-a2ui

What A2UI is, how actions work, what we found studying @a2ui/web_core, and how we'll build the renderer.

Based on concepts.md, actions.md, initial-study.md and renderer-plan.md

Concepts

The three pillars

Surface

Like a screen or widget

Isolation and lifecycle. Owns its components, data model and catalog. Several can be on screen at once.

Components

Like DOM elements

A flat list of typed components that point to their children by ID. Rendering starts at root.

Data model

Like a local state store

A JSON object per surface. Components read and write it through JSON Pointer paths: {"path": "/partySize"}

Two more pieces connect them: the catalog (which component types and functions a surface may use) and actions (the way back from client to agent).
Concepts

Components are flat, data is bound

{ "updateComponents": {
  "surfaceId": "booking",
  "components": [
    { "id": "root", "component": "Column",
      "children": ["title", "size", "submit"] },
    { "id": "title", "component": "Text",
      "text": "Book a table" },
    { "id": "size", "component": "TextField",
      "value": { "path": "/partySize" } },
    { "id": "submit", "component": "Button", ... }
  ] } }

Why flat?

  • Easy for LLMs to generate
  • Can be streamed in any order
  • Any component can be replaced by ID

Data model

  • Agent writes with updateDataModel; only bound components re-render
  • User writes through inputs, locally, with no network call
Concepts

Catalog negotiation

Client advertises supportedCatalogIds on every message
→
Agent picks the best match in createSurface.catalogId
→
Locked for that surface's lifetime

Why a list?

  • Several agents: each picks the first ID it understands
  • Migrations: list v2 and v1 so app and agent ship independently
  • Per-surface choice: custom catalog for one surface, basic for another

Rules

  • IDs only, not schemas: the agent must already know each ID
  • Different contents → new ID; breaking change → new version
  • Custom catalog first, basic catalog as fallback
Actions

Two action models

functionCall event
Intent Immediate, no network round trip Data for the agent to process
Agent informed No Yes
Defined by The catalog (zod schema, checked on device) The agent (free string, not checked)
Delivered to The catalog function The host's actionHandler
Typical use Open URL, switch tab, validation Submit, bid, save
Convention: functionCall for anything without a network round trip, event for anything the agent should handle. Both end in host code, so these are defaults, not hard limits.
Actions

How an action connects the pillars

user types "4"     TextField writes /partySize = 4      (local, no network)
user taps "Book"   Button.action fires
  ├─ functionCall → catalog function runs on device     (agent not told)
  └─ event        → context resolved from data model
                  → { action: { name: "book", surfaceId: "booking", context: { size: 4 } } }
                  → host actionHandler → agent
agent replies      updateDataModel / updateComponents / deleteSurface

Originates from a component

sourceComponentId

Reads the data model

Its context, or the whole model with sendDataModel: true

Scoped to a surface

The agent's reply targets the same surfaceId

Actions

Who owns what

Agent (server)

Handles events, calls business APIs, replies with updates. Must implement surfaces: lifecycle, state per surfaceId, and a client → agent path.

Host app

Catalog functions (device behaviour) and the actionHandler (transport to the agent). Attaches capabilities and data model to outgoing metadata.

react-native-the-a2ui

Calls props.action() on press. No API knowledge.

Gotchas

  • openUrl does nothing on RN (window.open); the renderer swaps in Linking.openURL
  • Async function errors aren't caught by web_core; functions must catch their own
  • Event names aren't validated; without an actionHandler, events are dropped silently
Initial study

Reuse @a2ui/web_core, don't port it

Core is plain TypeScript

Data model, bindings, expressions, node resolver, message processing and validation never touch the DOM. Dependencies: zod, zod-to-json-schema, @preact/signals-core.

One packaging blocker

The v0_9 and basic catalog entry points also load the Lit web components, which extend HTMLElement at load time. Metro doesn't tree-shake, and exports blocks deep imports.

React renderer

The surface layer (~720 lines) carries over almost unchanged. The 18 basic catalog components (~1,300 lines) need a native rewrite.

Initial study

Runtime risks on Hermes

Item Risk
\p{XID_Start} regex Fails at module load if unsupported; everything breaks. Check first.
Intl.PluralRules Probably missing; plan on @formatjs/intl-pluralrules
Intl.NumberFormat / DateTimeFormat Verify options on Android
window.open Silent no-op; replace with Linking.openURL
crypto.randomUUID Already has a fallback
Spike result: root entry loads 57 modules with no Lit; with a Metro alias the iOS bundle has 60 web_core modules and 0 Lit modules. The regex is still waiting on a device run.
Renderer plan

Key decisions

Core logic

Depend on @a2ui/web_core; don't port or copy it.

Lit workaround

A Metro helper withA2ui (plus a Jest helper) exposes three Lit-free virtual subpaths.

Long-term fix

Upstream PR adding those subpaths. Then the helpers are deleted, with no import changes.

Scope

Only what React Native core can build. No third-party UI, media or markdown libraries.

Extension point

The custom catalog only. A host component with the same name replaces ours.

Peer deps

react, react-native, @a2ui/web_core ~0.12.0, zod ^3.25.

Component support

Supported (13): built from RN core

TextImageRowColumnListCardDividerTabsModalButtonTextFieldCheckBoxChoicePicker

Unsupported (5): host adds them with its own libraries

IconVideoAudioPlayerSliderDateTimeInput

  • CheckBox uses Switch; Tabs and ChoicePicker are custom-built from primitives
  • Unknown component → error to the agent, small placeholder, one-time dev warning
Renderer plan

Customizing the catalog

import { MaterialIcons } from '@expo/vector-icons'
import {
  createBasicCatalog,
  createComponentImplementation,
  IconApi,
} from 'react-native-the-a2ui'

const Icon = createComponentImplementation(
  IconApi,
  ({ props }) => (
    <MaterialIcons name={toSnakeCase(props.name)} />
  ),
)

const catalog = createBasicCatalog({
  components: [Icon],
})

Catalog ID

  • Keep the basic ID when adding unsupported components or replacing one with the same props
  • Use your own ID when changing a component's schema or adding new types

Renderer plan

Phases

  1. Package skeleton: Metro/Jest helpers, surface layer port, example app
  2. Theme and styling: tokens, primaryColor variants, style slots
  3. Layout and display: Text, Image, Row, Column, List, Card, Divider, Tabs, Modal
  4. Input: Button, TextField, CheckBox, ChoicePicker, validation errors
  5. Unsupported components and docs: placeholder, dev warning, example with Expo libraries
  6. Functions and Intl: openUrl override, PluralRules polyfill, Android checks
  7. Upstream: PR the three subpaths into web_core, then delete the helpers (can start any time)
